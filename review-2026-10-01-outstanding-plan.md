**R5b (ruled 2026-10-03, both modes).** A link does not reach a remotely evaluated scratch intermediate: it has it evaluated again, here. A cell, anonymous node, intermediate link or transformer that (a) is scratch, (b) has a known checksum and (c) must be materialized, directly (`Transformation.run()`) or because an Expression is applied to it, is never placed at the jobserver or daskserver. It is evaluated here, and nothing is written.
- **Ban and no ban** (the author's reasoning). A scratch flag is a ban on publishing; a request without one may publish.
  - **Without a ban, placement is optimistic.** If the input bytes are not in this process, dispatch without asking the hashserver: if the hashserver has the bytes, the executing side is closer to them; if it doesn't, a resource private to the executing side (a read folder there) may still have them.
  - **With a ban, a materialization cannot be dispatched,** so it is tried here anyway, and the hashserver may come to the rescue.
  - **Every intermediate the code builds today carries the ban:** bound anonymous nodes, and standalone folded inputs (`expression_class.py:104-106`; a folded Cell's own `scratch` does not survive the folding, and need not). Path + path fuses at construction (`:132-140`), so an intermediate exists only behind a fusion barrier (a buffer-producing conversion, or a deep step), where it is often about as large as its input. The ban trades a download of the input for not storing a second copy.
- **The knob is ownership.** To have an intermediate evaluated where the data is and written, own it. Bound, name it: named nodes are non-scratch by default. Standalone, call `compute()` on the intermediate Cell itself: it then owns its own last link, non-scratch by default. Its bytes are then reachable, so the folded link that carries the ban never has to materialize anything. The ban governs what the chain writes, not whether it may use a published result.
- **The first evaluation is placed as usual**, and may be remote. The author chose this over evaluating a cache-missing intermediate here at once: an Expression evaluated where the data is costs almost nothing, and an invalid one fails there, before anything is downloaded. Fail fast is worth the second evaluation, as it was for `run()` on a scratch Transformation (ruled 2026-09-29).
- **Materialization is on demand**: only when the next link must be evaluated (a cache and database miss) and needs bytes that are not reachable (`_result_reachable`: memory or hashserver). A next link answered from the caches needs no bytes, so nothing is downloaded.
- **It is not a fingertip**: there is no provenance walk, because the owner holds the recipe. So "an Expression never fingertips its input" stands. It is placed like one, though (`scratch-witness-audit.md`, case 2: local even while a jobserver is active, nothing written).
- **Consequences for the contract.** Fail fast covers the first link of a chain only: once an intermediate is materialized here, the next link's input is in memory and it runs here too, so an invalid later link fails after the download. Materializing an Expression needs only seamless-core, but recomputing a scratch transformer needs its environment in this process: a Context on a thin client cannot run a scratch transformer whose scratch result an Expression edge reads (the restriction `run()` already has).

**R5, standalone (ruled 2026-10-03).** In a standalone chain only two objects carry a scratch policy: the Cell that owns the chain, and a source Transformation at its root. Building the chain folds every Cell input into that Cell's own Expression (`Expression.__post_init__`, `expression_class.py:104-106`), so every link in between is a naked Expression, which carries no scratch flag.
- **The Cell's own link** (the last one) carries the Cell's scratch, as a checksum request (`materialize=False`, ruled 2026-09-30). Unchanged.
- **Every intermediate link** is scratch, whatever the Cell's policy, and a checksum request (`materialize=False`): placed as usual, so possibly dispatched. When the next link needs its bytes and they are not reachable, it is evaluated again here (*R5b*). It is never written to the hashserver.
- **A source Transformation keeps its own policy.** When the first link needs its input buffer (a path, or `conversion_needs_buffer`), `compute()` asks the Transformation for its value (`require_value=True`) with no scratch override; a gone buffer is then recovered as for any value request on it (`_ensure_result_value`, a local fingertip, so this already obeys R5b). The getters never ask, because they never run a source: the first link then fails with `CacheMissError`, which becomes `.exception` (2026-09-14). Consequence: a non-scratch Cell whose only link is the identity over a scratch Transformation would hold a result that nothing writes; R5d makes it overrule the Transformation instead (`scratch_override=False`), because the Transformation's result is the Cell's own buffer. A Transformation behind a path or a buffer-producing conversion is not overruled.
- Bound handle reads go through the same helper (`builder_state.py:214`), so they follow this rule, which agrees with "anonymous nodes are always scratch".

## Phase 2 — seamless-workflow: `build()` and handle methods never do work, and build the contract's Expression

These findings share one cause: `build()` assembles its Expression by its own logic, which evaluates intermediate conversions and fuses differently from the derivation and from handle reads. Rewrite it once.

- **Finding 6 (probe-confirmed):** `ctx.b.as_celltype("plain")[3].build()`, on a handle and on a named node alike, leaves the `text→plain` Expression in the process cache: `build()` evaluated it (`_build_conversion_expression` and `project()` call `.compute()`). Contract: `cells.md`, *Work*: `build()` does no work. It runs on the controller loop, ignores `expression_execution`, raises `RunningLoopRefusal` when the parent's buffer is not here, and blocks the controller when it is.
- **Finding 8 (probe-confirmed):** for `ctx.b["x"].as_celltype("plain")["y"]` (`b` mixed), `build()` returns the single fused `(b, "x.y", mixed, plain)`, while the node evaluates two links. Contract: `expressions.md`, *Fusion*: a conversion that follows a path closes the run.
- **Finding 9 (probe-confirmed):** for a plain cell `a` set with `set_checksum(cs, input_celltype="text")`, `ctx.a.as_celltype("mixed").build()` returns `(cs, "", text, mixed)`, i.e. `text→str`, instead of `(cs, "", plain, mixed)`. The run must be rooted at the node's own checksum and celltype.
- **Handle `build()` fuses upstream through named nodes** (handle-read agent, item 6), so its identity can differ from the Expression its reads evaluate over the parent's checksum.
- **`fingertip()` on a handle forces the handle's evaluation** (handle-read agent, item 7). Contract: `fingertip()` never forces `.checksum`.

**The fix.** `build()` returns the chain as nested Expressions, each link's input being the previous link's Expression (an Expression input is a legal identity: `("expression", …)`), rooted at the node's own current checksum and celltype, decomposed with the same function the derivation and the handle reads use (`graph.anonymous_links` plus the fusion rules), and never evaluated. A named consumer fuses through its source exactly as the derivation does, no more. `fingertip()` on a handle fingertips the handle's recorded result checksum, or returns `None` when there is none, as `Pin.fingertip()` does.

**Tests:** one test per bullet above, each asserting the returned identity and that the Expression cache is unchanged by `build()`; the probes in this session's scratchpad (`test_zz_probe_review.py`) are a starting point.
