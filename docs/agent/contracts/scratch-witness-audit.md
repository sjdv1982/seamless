# Scratch, Witness Outputs, and Auditing (Contract)

Seamless validates equality at the checksum level: byte-identical content (or deep-structure identity).
Anything “tolerance-based” requires a separate user-defined witness/comparison step.

## Scratch

Scratch is an optimization knob:
- Scratch allows bulky intermediates to be dropped (not materializable later).
- Scratch plus input fingertipping is also a placement mechanism: if a downstream transformation needs a missing scratch input, the producer transformation is rerun where the consumer needs the bytes.
- Use scratch for bulky generated intermediates that are not meaning-bearing and whose main purpose is to feed another transformation.
- Scratch must not remove the ability to evaluate the meaning-bearing outcome of the computation.

**Scratch applies to the result, never to the transformation's definition or inputs.** The transformation dict (its `tf_checksum` buffer) is provenance: fingertipping a scratch result, possibly in another process, starts from it. Nothing produces a definition, so nothing could fingertip one back. A transformation therefore always writes its definition to the hashserver, scratch or not. Its inputs (pins, code, modules) follow their own rule, which the transformation's scratch plays no part in: a literal pin is always published, and any other pin is scratch exactly when the consuming transformation fingertips its inputs (`contracts/pins.md`, *Scratch at the pin*). Only the result buffer is governed by the transformation's scratch.

Scratch is **orthogonal** to transformation identity: it controls whether a buffer is durably stored, not the value it denotes. The `result_checksum` is unchanged by scratch, scratch is excluded from `tf_checksum`, and two transformations differing only in scratch policy are cache-equivalent (see `contracts/identity-and-caching.md`). The "must not remove the ability to evaluate the meaning-bearing outcome" rule above is a *usage* constraint, not a checksum rule.

**A scratch transformation may be dispatched, and its result is not published** (ruled 2026-09-29), unless a non-scratch pin, or in a Context a non-scratch cell, needs it (below). A jobserver or Dask worker runs it like any other transformation, but writes no result buffer to the hashserver, so the requester receives only the result checksum. A consumer that needs the bytes recovers them by fingertipping. A consumer running on the server does this through an input fingertip (case 1 below), and on the client `Transformation.run()` fingertips the result, recomputing the transformation locally. **A dispatched scratch transformation whose value the client asks for therefore runs twice.** That is the accepted cost of scratch. `local=True` keeps a scratch transformation in the requesting process instead.

Input fingertipping is opt-in on each consumer transformation. Marking an upstream
producer as scratch does not automatically allow downstream consumers to
fingertip missing inputs. In Python, set the downstream transformer/core's
`allow_input_fingertip = True` before constructing the consuming transformation;
for CLI execution of a transformation checksum, use `--fingertip`.

**The consumer's opt-in decides whether a result it holds stays scratch.** A consumer that fingertips its inputs has scratch pins (literals apart), so a scratch producer whose result is the pin's own input stays scratch. A non-scratch pin overrules a scratch producer when it holds that producer's result; the same holds for a non-scratch Cell. A path or buffer-producing conversion stops that overrule, and earlier Expression links remain scratch checksum requests (`contracts/pins.md`, *Scratch at the pin*; `contracts/cells.md`, *Scratch policy*).

Two things that do **not** make a scratch result materializable:

- **Reading a handle.** `Cell.buffer`, `Cell.value` and `Pin.value` resolve and never fingertip; only an explicit `compute()`, `Transformation.run()`, `Cell.fingertip()` or `Pin.fingertip()` does work (`contracts/cells.md`).
- **Attaching or mounting.** A delivery to a file or directory resolves the payload and never fingertips, so mounting an output is not a way to force a scratch producer to re-run or to make its result durable (`contracts/attachments.md`, *A delivery resolves; it never computes*).

What *does* keep a scratch result alive once it exists is explicit public interest in it: an explicitly requested scratch result acquires a refholder claim and is protected from eviction, while an unrequested one stays purgeable (`contracts/internal/checksum-reference-lifecycle.md`, §8).

Agent porting implication: do not replace a compact, reliable producer implementation just to avoid a large edge. If the producer is deterministic and cheap enough to rerun, prefer a scratch producer plus fingertipping consumer so the large value is materialized co-located with the consumer.

**Determinism note.** A `scratch` producer is *always* regenerated by fingertipping when its output is needed, so it **must be reproducible**. But the surfacing of non-reproducibility is precisely a property of **fingertipping** (the recomputation), *not* of scratch as such — see the next section.

## Fingertipping

Fingertipping is a **Checksum → Buffer resolution mode**, and is *distinct* from scratch — scratch is a **storage policy** ("do not durably store this buffer"), fingertipping is a **retrieval-with-recomputation-fallback**. When a buffer is requested with fingertipping enabled, Seamless:

1. tries normal **retrieval** first — the local buffer cache, then the hashserver;
2. **only if the buffer is absent**, falls back to **fingertipping proper**: *recomputation-using-provenance*. It consults the **reverse-checksum cache** (`rev_transformations` / `rev_expression`, and the reverse rows of cell joins) to find a transformation, an Expression or a cell join that *produces* the requested checksum, recomputes it — recursively fingertipping that producer's own inputs — and so regenerates the buffer.

**In a fingertip chain, a cell join is a link like any other.** A cell join is the Expression behind a cell-level join (`contracts/expressions.md`, *Cell joins*). When a fingertip reaches one through its reverse row, the celljoin JSON is read from this process or from the hashserver (the database holds none), its inputs are fingertipped and it is re-evaluated in the process that wants the buffer. An ordinary evaluation of a cell join is different: there, an input whose buffer is neither local nor on the hashserver is a final `CacheMissError`, with no recomputation. A deep join needs only its root index, so recovering its result never fingertips a member.

A buffer is **absent** — and so triggers the recomputation fallback — in two distinct cases:

- it was **evicted or deleted** from the store (e.g. removed from the hashserver dir) — which can happen to a **non-`scratch`** result; **or**
- it was **never stored** (`scratch`).

So `scratch` *guarantees* a buffer will need fingertipping when its value is required, but fingertipping is **not** exclusive to scratch: an evicted non-scratch buffer is regenerated by the same path. Fingertipping is opt-in per consumer (`allow_input_fingertip = True` in Python, `--fingertip` for a CLI transformation checksum).

### Where a fingertip chain runs, and what it leaves behind

**Fingertipping always runs locally and never writes to the hashserver.** There is no exception: not for a manual fingertip, not inside a job, not at any site, and not for the end result of a chain.

**A fingertip chain runs in the process that wants the buffer.** Nothing in it is dispatched, not the Expressions and not the Transformations. "Evaluated where the data is" governs ordinary Expression evaluation and does **not** govern fingertipping (`contracts/expressions.md`, *Fingertipping is exempt from "where the data is"*). The reason is structural: a remote evaluation answers with a *checksum*, so a remotely evaluated result could reach the requester only by being written to the hashserver, which would re-add exactly the buffer that a `scratch` decision or an eviction deliberately kept out. With a job server active, a fingertip happens in one of two cases:

**Case 1: input fingertip inside a job.** This is the common case: a big scratch intermediate that is only needed as input for a transformation. The consuming transformation is dispatched to the job server (jobserver or daskserver) like any other. When it runs, it fingertips its missing input **locally, as far as Seamless is concerned**. Nothing in that chain is dispatched again. On a daskserver the recomputation may run on another Dask worker, but Dask moves that data between workers itself, independently of Seamless. **Nothing is written to the hashserver**: not the recovered input, not any intermediate. The job wants the buffer for itself and has it in memory. This is scratch plus input fingertipping working as a placement mechanism (*Scratch*, above): the bulky input is regenerated where it is consumed.

**Case 2: manual fingertip.** Someone explicitly asks for the bytes of a Cell, Pin, Checksum or Expression result that was marked scratch (or evicted), in Python (`Checksum.fingertip()`, `Cell.fingertip()`, `Pin.fingertip()`, and `Transformation.run()`, which fingertips its result) or with the `seamless-fingertip` CLI. **Local evaluation is the norm, even while a job server is active**: the chain runs in the requesting process and is not dispatched, whole or in part. **Nothing is written to the hashserver** by the fingertip. A bare `Checksum.fingertip()` leaves the buffer in local memory only. A fingertip through a non-scratch owner persists the result, but through that owner's own incref, not because of the fingertip.

**A missing scratch intermediate in an Expression chain is materialized locally on demand.** When a later link needs bytes for a known scratch result whose buffer is unreachable, it evaluates that input again here and writes nothing. This uses the owner's known recipe, not the reverse-index fingertip search. The first link may be dispatched and fail before a download; once an intermediate is materialized here, later links run here too. A thin client cannot locally re-run a scratch Transformation whose execution environment exists only remotely (`contracts/expressions.md`, *The requester's scratch decision*).

**The rule both cases follow: the chain runs where the buffer is wanted, so the buffer is already in memory where it is needed and nothing is written.**

A chain's cost is bounded by the **frontier**, not by the ancestry: retrieval is tried at every level before recursing, so the walk stops at the first checksum the store can serve, and what is recomputed is the frontier of the absent region. The restriction to state alongside it: **fingertipping assumes that the process that wants the buffer can execute the chain's transformations.** In case 1 that is the job's worker. In case 2 it is the requesting process, so a thin client with no conda environment or no declared binaries cannot fingertip through a Transformation.

**Evaluating, recording identity and publishing are three different acts, and only the third stores anything.** The vocabulary is ruled: *publishing* is the buffer write, *recording* is what happens to a result checksum, and `contracts/internal/checksum-reference-lifecycle.md` uses the same two words in the same two senses.

| Act | Effect |
|---|---|
| **Evaluating** a transformation or Expression, or recovering a buffer by fingertipping | produces a buffer in that process's memory. That is all |
| **Recording identity** — the transformation and expression result caches, and the reverse index fingertipping walks | inserts a producer → result checksum once. A different result is never recorded as the canonical result; it is an irreproducible observation and says nothing about where any buffer is |
| **Publishing** — writing the result buffer to the hashserver | nothing more: it takes no claim and asserts nothing about who holds the result (ruled 2026-09-29). A scratch result is never published |

**Neither evaluation nor fingertipping publishes of its own accord.** A result is published in exactly two ways. Either an owner increfs it non-scratch, for example a non-scratch Cell; that incref also overturns any scratch status (`contracts/internal/checksum-reference-lifecycle.md`). Or a non-scratch dispatch asks the executing side to write it, because the hashserver is the only channel by which the bytes can reach the requester (below). So a bare `Checksum.fingertip()` leaves nothing behind but a buffer in local memory; a Cell-level fingertip on a non-scratch Cell persists the result, because the Cell increfs it. The fingertip site itself never decides: it holds a bare checksum, with no owner and no scratch intent.

**No site is exempt, and nothing is ever written.** The rule holds wherever the recovery happens: on a client, inside a jobserver, on a Dask worker. A worker that fingertips a missing `scratch` input (case 1) is the ordinary case, not an exception: it wants the buffer for itself, and persistence stays the holder's act. A manual fingertip (case 2) is not an exception either. **There is no exception**: no process fingertips on another process's behalf, so no fingertip ever needs the hashserver to hand its result over. The only writes made on somebody else's behalf are *dispatched evaluations* carrying `scratch=False`, such as a dispatched `Expression.run()` or a non-scratch transformation (`contracts/expressions.md`, *The requester's scratch decision*). Those are evaluations, not fingertips. A remote fingertip request does not exist; adding one would be a new feature that needs its own contract ruling.

**The consequence for a reader:** a result checksum never implies a result buffer, and a fingertip is the only guaranteed way to get one (`contracts/expressions.md`, *Results and caching*).

**When the walk cannot recover the buffer, it reports a category.** `CacheMissError(checksum).fingertip_category` is the highest-ranked outcome among all candidates, including nested fingertips: `materialization`, `failed_transformation`, `irreproducible_transformation`, or `irreproducible_expression` (`contracts/expressions.md`, *What a failed fingertip reports*). Candidate trial order does not affect the maximum. Cancellation and infrastructure errors propagate without a category. The reverse index, execution records, automatic irreproducible rows, and hashserver index remain the investigation route; the exception does not carry a candidate traceback.

*Implemented:* neither branch of the walk publishes. A tempref never writes, and both branches mark the buffer they recover as scratch, so a fingertip (case 1 or case 2) leaves the recovered buffer in memory only. This includes the Dask fat-input task: `seamless-dask/seamless_dask/client.py` `_fingertip_buffer_async` temprefs the fingertipped buffer and marks it scratch (fixed in seamless-dask `9ebe5fd`). See `contracts/expressions.md`, *Status: publication and fingertipping*.

**What "never dispatched" does and does not exclude.** The chain itself sends no work to a server: none of its links is dispatched. Two ways of reaching remote work are correct and do not break that rule:

- **A recompute may join remote work already in flight** for the same identity instead of starting local work. A transformation candidate joins a jobserver submission of the same `tf_checksum` that is already running (`TransformationCache._run_active_or_execute`). An Expression candidate joins a dispatched evaluation through the shared member set (`contracts/expressions.md`, *Deduplication*), and `materialize` is not applied to that join. Joining is deduplication, not a dispatch: that work was sent by its own requester, and that link is then served remotely.
- **Transformations launched by a candidate's own code are not forced local.** The recompute of the candidate runs locally (`force_local`), but a transformation that its code launches is new work, not a link of the chain, and it goes through the ordinary jobserver and Dask paths.

### Two modelling rules that keep a graph out of the expensive shape

Fingertipping a large parent in order to keep one small item is the case where local evaluation is genuinely the costly choice. It is reachable only by opting into it, and two rules keep a graph out of it:

- **Do not scratch a small derived cell.** If it is stored, ordinary resolution serves it and no chain is built at all. Scratch is for *bulky* intermediates; applying it to a small projection buys nothing and can force the recomputation of its large parent.
- **Make an item-addressed large parent deep.** A path step over a `deepcell` / `deepfolder` / `folder` checksum selects a **sub-checksum without materializing the parent** (`contracts/deep-celltypes.md`), so the item is reachable without the parent ever existing as a buffer. A large `plain` blob that consumers index into is the shape to avoid.

**Fingertipping is where accidental nondeterminism surfaces.** Step 1 (retrieval) is pure lookup and can never diverge. Step 2 **re-executes the producer**; a different result checksum breaks the requested input identity, reports `irreproducible_transformation`, and adds an automatic irreproducible row while preserving the original forward result. A normally stored, never evicted result hides such nondeterminism until recomputation (see `contracts/identity-and-caching.md`, "Caching masks accidental nondeterminism"). Practical rule: **any buffer that may be fingertipped — every `scratch` producer, and in principle any evictable buffer — must be reproducible.**

## Provenance: the derivation graph

**The provenance of a result is its derivation: the graph of productions that leads to it.** A node is a recorded producer, of which there are three kinds: a Transformation, an Expression, and a cell join. An edge exists wherever one producer's result checksum is another producer's input. This graph is the object of study. Materialization, placement and cache reuse are out of scope: where a step ran, whether a buffer was stored, and which session reused a recorded result are not part of a result's provenance. An execution record still says where and when the recorded production ran (`contracts/execution-records.md`).

**The walk.** It starts from a result checksum, chosen by whoever wants to know where that result came from, and uses the same reverse rows as fingertipping (*Fingertipping*), without recomputing anything:

| Producer | Found through | What it tells |
|---|---|---|
| Transformation | its reverse row, then the transformation dict on the hashserver | each pin by name, with its celltype and checksum; the language, the output and, for compiled code, the schema; the code checksum, which resolves to the source |
| Expression | its reverse row, which is the recipe itself | the input checksum, the path and the two celltypes |
| cell join | its reverse row, then the celljoin JSON on the hashserver | which input went under which key, and the root |

A deep index resolves to its member names. A module pin and a compiled-objects pin are self-describing: the source is in the buffer. The execution record adds the environment.

**In a workflow Context the derivation is complete.** Every step by which a Context derives one checksum from others is one of the three producers, so the walk reaches the leaves without a break. The cell join is what closes it: until cell joins are implemented, a join's result has no producer row and the walk stops there (`contracts/cells.md`, *Gaps*).

**What it is sufficient for.** The derivation is enough to reconstruct the completed workflow as a DAG and to tell what was computed, in a sense that is not specific to Seamless, provided the transformation code is readable. It is not the Context graph, and it is not meant to be. Node names, and configuration outside identity such as scratch policy and environment, are saved by `get_graph()` and are not in the derivation; pin names and join keys are. A checksum may have several recorded producers, because computations converge: each of them is a valid derivation.

**A leaf is original data, or a coverage gap.** A leaf is a checksum with no recorded producer. Ideally the leaves are the original data: the diffraction patterns, not the coordinate file derived from them. A leaf that is in fact a computed value marks a **coverage gap**, a derivation that happened outside Seamless:

- a value computed by an external tool and brought in as an input;
- host-language glue between recorded steps: a result that is read into Python in a script or a notebook, modified, and passed on as a new value. A workflow Context has no such glue, since its wiring consists of Expressions and cell joins;
- a sub-path write of a checksum, which embeds that checksum's value into the root literal (`contracts/cells.md`, *Projections*). It is a one-off assembly, and the link is not kept.

Inside a driver transformation, glue between the transformations it launches is part of the driver's own code, so it can be read from the source. **The link from a driver to the transformations it launched belongs to the derivation**: it is what lets a walk open a driver up into the steps it ran. It is not recorded yet (*Gaps*, below).

**Seamless is meant to federate.** An identity is content-addressed, so it means the same thing in every database, and a row recorded in one `seamless.db` is valid in any other. There is one logical database of derivations, of which each `seamless.db` holds a shard. A leaf in one shard may be a result in another, and the walk then continues there. Two shards that record different results for one identity do not conflict: that is an observation of irreproducibility (`contracts/execution-records.md`).

**Whether the bytes are still there is a different question.** Whether a leaf's buffer can still be retrieved, how a leaf is described, and whether the definitions the walk reads are kept, are matters of data stewardship (FAIR), not of computation provenance. Seamless contributes one guarantee to it: a transformation's definition is published whatever its scratch policy (*Scratch*), and a celljoin JSON is written to the hashserver whenever it is recorded (`contracts/expressions.md`, *Cell joins*).

**Gaps.** Two parts of the derivation are not recorded today:

- **Cell joins are not implemented.** A join's result has no producer row, so a walk stops at every join (`contracts/cells.md`, *Gaps*).
- **The driver link is not recorded.** A transformation launched by a driver's code is recorded as a producer in its own right, and its inputs and result connect to other producers by checksum as usual. That the driver launched it is recorded nowhere, so a walk sees the driver as one opaque step and cannot open it up, and the launched transformations cannot be attributed to it. All a launched transformation carries is a boolean, `__meta__["driver"]`, set when it is built while a driver is running; it is outside identity and names no parent. The parent's `tf_checksum` is not passed along when the launch is submitted, and neither the database nor the execution record has a place for the link (`contracts/execution-records.md`).

## Witness outputs (do not scratch)

A witness is a small, persistent artifact that encodes scientific meaning and diagnostics, e.g.:
- classifier: `(label, margin)` (or other stability diagnostics)
- simulation: `(ΔE, uncertainty/diagnostics)`

Witness outputs should be stored non-scratch so they remain comparable even when large artifacts are unavailable.

## Auditing / falsification via recomputation

Recommended audit procedure for a specific computation:
1) Retrieve the cached result (if available) and record its checksum and environment signature.
2) Force a recomputation (bypass transformation-result caches).
3) Compare:
   - first, bitwise: checksum equality (best-case)
   - if unequal, compare witness outputs (which is itself a transformation that returns a boolean or verdict artifact)
4) If the witness comparison fails, treat this as evidence of environment sensitivity or underspecification:
   - tighten the environment envelope, or
   - refine the witness/observable, or
   - make implicit inputs explicit (closures/config, determinism knobs).

## Environment signature

Even when cache keys are environment-agnostic, record per-run environment information to support audits:
- major library versions/backends
- hardware/OS basics
- determinism-relevant knobs (threads, math modes) when applicable
