# Scratch, Witness Outputs, and Auditing (Contract)

Seamless validates equality at the checksum level: byte-identical content (or deep-structure identity).
Anything “tolerance-based” requires a separate user-defined witness/comparison step.

## Scratch

Scratch is an optimization knob:
- Scratch allows bulky intermediates to be dropped (not materializable later).
- Scratch plus input fingertipping is also a placement mechanism: if a downstream transformation needs a missing scratch input, the producer transformation is rerun where the consumer needs the bytes.
- Use scratch for bulky generated intermediates that are not meaning-bearing and whose main purpose is to feed another transformation.
- Scratch must not remove the ability to evaluate the meaning-bearing outcome of the computation.

Scratch is **orthogonal** to transformation identity: it controls whether a buffer is durably stored, not the value it denotes. The `result_checksum` is unchanged by scratch, scratch is excluded from `tf_checksum`, and two transformations differing only in scratch policy are cache-equivalent (see `contracts/identity-and-caching.md`). The "must not remove the ability to evaluate the meaning-bearing outcome" rule above is a *usage* constraint, not a checksum rule.

Input fingertipping is opt-in on each consumer transformation. Marking an upstream
producer as scratch does not automatically allow downstream consumers to
fingertip missing inputs. In Python, set the downstream transformer/core's
`allow_input_fingertip = True` before constructing the consuming transformation;
for CLI execution of a transformation checksum, use `--fingertip`.

Two things that do **not** make a scratch result materializable:

- **Reading a handle.** `Cell.buffer`, `Cell.value` and `Pin.value` resolve and never fingertip; only an explicit `compute()`, `Transformation.run()`, `Cell.fingertip()` or `Pin.fingertip()` does work (`contracts/cells.md`).
- **Attaching or mounting.** A delivery to a file or directory resolves the payload and never fingertips, so mounting an output is not a way to force a scratch producer to re-run or to make its result durable (`contracts/attachments.md`, *A delivery resolves; it never computes*).

What *does* keep a scratch result alive once it exists is explicit public interest in it: an explicitly requested scratch result acquires a refholder claim and is protected from eviction, while an unrequested one stays purgeable (`contracts/internal/checksum-reference-lifecycle.md`, §8).

Agent porting implication: do not replace a compact, reliable producer implementation just to avoid a large edge. If the producer is deterministic and cheap enough to rerun, prefer a scratch producer plus fingertipping consumer so the large value is materialized co-located with the consumer.

**Determinism note.** A `scratch` producer is *always* regenerated by fingertipping when its output is needed, so it **must be reproducible**. But the surfacing of non-reproducibility is precisely a property of **fingertipping** (the recomputation), *not* of scratch as such — see the next section.

## Fingertipping

Fingertipping is a **Checksum → Buffer resolution mode**, and is *distinct* from scratch — scratch is a **storage policy** ("do not durably store this buffer"), fingertipping is a **retrieval-with-recomputation-fallback**. When a buffer is requested with fingertipping enabled, Seamless:

1. tries normal **retrieval** first — the local buffer cache, then the hashserver;
2. **only if the buffer is absent**, falls back to **fingertipping proper**: *recomputation-using-provenance*. It consults the **reverse-checksum cache** (`rev_transformations` / `rev_expression`) to find a transformation/expression that *produces* the requested checksum, recomputes it — recursively fingertipping that producer's own inputs — and so regenerates the buffer.

A buffer is **absent** — and so triggers the recomputation fallback — in two distinct cases:

- it was **evicted or deleted** from the store (e.g. removed from the hashserver dir) — which can happen to a **non-`scratch`** result; **or**
- it was **never stored** (`scratch`).

So `scratch` *guarantees* a buffer will need fingertipping when its value is required, but fingertipping is **not** exclusive to scratch: an evicted non-scratch buffer is regenerated by the same path. Fingertipping is opt-in per consumer (`allow_input_fingertip = True` in Python, `--fingertip` for a CLI transformation checksum).

### Where a fingertip chain runs, and what it leaves behind

**A fingertip chain runs entirely in the requesting process.** Nothing in it is dispatched — not the Expressions, not the Transformations. "Evaluated where the data is" governs ordinary Expression evaluation and does **not** govern fingertipping (`contracts/expressions.md`, *Fingertipping is exempt from "where the data is"*). The reason is structural rather than a preference: a remote evaluation answers with a *checksum*, so a remotely evaluated result could reach the client only by being written to the hashserver — which would re-add exactly the buffer that a `scratch` decision or an eviction deliberately kept out. Local evaluation materializes it in process memory only.

Its cost is bounded by the **frontier**, not by the ancestry: retrieval is tried at every level before recursing, so the walk stops at the first checksum the store can serve, and what is recomputed is the frontier of the absent region. The restriction to state alongside it: **fingertipping assumes the requesting process can execute the chain's transformations.** A thin client with no conda environment or no declared binaries cannot fingertip through one.

**Evaluating, recording identity and publishing are three different acts, and only the third stores anything.** The vocabulary is ruled: *publishing* is the buffer write, *recording* is what happens to a result checksum, and `contracts/internal/checksum-reference-lifecycle.md` uses the same two words in the same two senses.

| Act | Effect |
|---|---|
| **Evaluating** a transformation or Expression, or recovering a buffer by fingertipping | produces a buffer in that process's memory. That is all |
| **Recording identity** — the transformation and expression result caches, and the reverse index fingertipping walks | stores the mapping producer → result checksum. It must keep happening, and it says nothing about where any buffer is |
| **Publishing** — writing the buffer to the hashserver | an assertion that somebody holds the result and will want it later |

**Neither evaluation nor fingertipping publishes.** Publication is the act of increfing the buffer for non-ephemeral interest — for example through a non-scratch Cell — and that single act both writes the buffer and overturns any scratch status (`contracts/internal/checksum-reference-lifecycle.md`). So a bare `Checksum.fingertip()` leaves nothing behind but a buffer in local memory; a Cell-level fingertip on a non-scratch Cell persists the result, because the Cell increfs it. The fingertip site itself never decides: it holds a bare checksum, with no owner and no scratch intent.

**No site is exempt, and no intermediate is ever written.** The rule holds wherever the recovery happens — on a client, inside a jobserver, on a Dask worker. A worker that fingertips a missing `scratch` input is the ordinary case, not an exception: it wants the buffer for itself, and persistence stays the holder's act. Making it depend on *where* a recovery happened is precisely what this rule exists to prevent. The one genuine exception is a fingertip performed **on somebody else's behalf** — a remote fingertip *request* — which must write the buffer of the fingertipped checksum, since there is no other channel by which the requester can receive it; even then it writes **only the end result of the chain**, never an intermediate.

**The consequence for a reader:** a result checksum never implies a result buffer, and a fingertip is the only guaranteed way to get one (`contracts/expressions.md`, *Results and caching*).

*Contract ahead of code:* Expression evaluation publishes its result buffer today, for **every** evaluation — so a fingertip currently re-adds to the hashserver exactly what it recovered. The transformation branch of the same walk does not have this defect. See `contracts/expressions.md`, *Status: publication and fingertipping*.

### Two modelling rules that keep a graph out of the expensive shape

Fingertipping a large parent in order to keep one small item is the case where local evaluation is genuinely the costly choice. It is reachable only by opting into it, and two rules keep a graph out of it:

- **Do not scratch a small derived cell.** If it is stored, ordinary resolution serves it and no chain is built at all. Scratch is for *bulky* intermediates; applying it to a small projection buys nothing and can force the recomputation of its large parent.
- **Make an item-addressed large parent deep.** A path step over a `deepcell` / `deepfolder` / `folder` checksum selects a **sub-checksum without materializing the parent** (`contracts/deep-celltypes.md`), so the item is reachable without the parent ever existing as a buffer. A large `plain` blob that consumers index into is the shape to avoid.

**Fingertipping is where accidental nondeterminism surfaces.** Step 1 (retrieval) is pure lookup and can never diverge. Step 2 **re-executes the producer**; if that producer is not reproducible, the regenerated buffer has a **different checksum** than the one requested, breaking the input identity of whatever asked for it. A normally-stored, never-evicted result hides such nondeterminism forever — it is looked up, never recomputed (see `contracts/identity-and-caching.md`, "Caching masks accidental nondeterminism"). Practical rule: **any buffer that may be fingertipped — every `scratch` producer, and in principle any evictable buffer — must be reproducible.**

## Witness outputs (do not scratch)

A witness is a small, persistent artifact that encodes scientific meaning and diagnostics, e.g.:
- classifier: `(label, margin)` (or other stability diagnostics)
- simulation: `(ΔE, uncertainty/diagnostics)`

Witness outputs should be stored non-scratch so they remain comparable even when large artifacts are unavailable.

## Auditing / falsification via recomputation

Recommended audit procedure for a specific computation:
1) Retrieve the cached result (if available) and record its checksum and environment signature.
2) Force a recomputation (bypass transformation-result caches).
3) Compare:
   - first, bitwise: checksum equality (best-case)
   - if unequal, compare witness outputs (which is itself a transformation that returns a boolean or verdict artifact)
4) If the witness comparison fails, treat this as evidence of environment sensitivity or underspecification:
   - tighten the environment envelope, or
   - refine the witness/observable, or
   - make implicit inputs explicit (closures/config, determinism knobs).

## Environment signature

Even when cache keys are environment-agnostic, record per-run environment information to support audits:
- major library versions/backends
- hardware/OS basics
- determinism-relevant knobs (threads, math modes) when applicable
